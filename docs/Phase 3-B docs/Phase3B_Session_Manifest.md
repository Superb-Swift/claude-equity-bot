## How new chats work (why this manifest exists)

Claude's workspace **resets between conversations**. Memory carries the project's *story* (phases, verdicts, constraints, conventions — including that we're in 3-B on generator era **A-S1D1**) but **not file contents** — so every new chat needs its working files uploaded fresh, or pulled from the repo (Option B). Within a single conversation files persist across messages; you only re-upload when data changes (a new day's tracker/log) or after you edit a file (e.g. splicing the notes).

**Source-of-truth rule:** uploaded files always win. The repo lags your working tree between pushes, so upload *your current* `analyst_notes.md` and tracker — not the repo copies — whenever they're ahead.

## New in 3-B — modules & conventions (so a fresh chat isn't surprised)

- **New modules:** `signal_state.py` (S1 state persistence — raw-confidence chain, last 5/ticker, atomic save, degrades to `{}`) and `seed_signal_state.py` (one-shot seed/restore from the tracker; overlays RAW confidence from the logs so a re-seed is exactly-raw and idempotent).
- **Generator era `A-S1D1`** (`PROMPT_VARIANT` in `main.py`) — a version stamp, **not** an A/B arm (the A/B program stays terminated). S1 = prior-signal state input; D1 = the confidence-damping rule in `risk_engine.py`.
- **Two-channel logging** — every signal line carries `confidence` (operative, damped → the tracker) **and** `confidence_raw` (the model's own output → the audit/acceptance channel). Tags: `H1[…] | S1[prior=…; dconf=…] | D[raw=…; op=…; trail=…; damp=…]`.
- **Phase tag** `[PHASE 3-B DRY RUN]` — parsers are phase-agnostic as of this deploy (the ACCOUNT_RE fix); the literal "DRY RUN" is load-bearing for `analyze_log`.
- **Seed / re-seed discipline** — run `python seed_signal_state.py --tracker tracker_with_registry.xlsx` before the first live day, and again after any PM diagnostic run (a PM run overwrites the day's state entries). Verify the printed chains end at the last resolved date.
