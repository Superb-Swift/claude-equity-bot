## 2 · N-1 · YTD rendered as quarterly

### The proof

`[V]` `python edgar_client.py --xbrl PWR`. Both buckets sit in the **same accession**, `0001050915-26-000025`:

| Line | 180d [H] `2026-01-01 → 06-30` | 90d [Q] `2026-04-01 → 06-30` | Rendered under "10-Q Q2 FY2026" |
|---|---|---|---|
| Revenue | $17,431,784,000 | $9,556,997,000 | **$17.4B** |
| Gross profit | $2,652,507,000 | $1,545,178,000 | **$2.7B** |
| Operating income | $1,033,613,000 | $694,834,000 | **$1.0B** |
| Net income | $672,006,000 | $451,381,000 | **$672.0M** |
| Diluted EPS | 4.41 | 2.96 | **4.41** |

The quarterly bucket existed and was passed over on every line. Per §10.2's own dichotomy this is a **CLIENT bug, not a filer tagging quirk** — the diagnostic did exactly the job it was built for.

Corroborated against each name's own 8-K in the same section: PWR 8-K reports Q2 revenue $9.6B; FTI MD&A $2,763.1M; RTX 8-K $24.7B; GM 8-K $48.0B; PM 8-K Q2 diluted EPS $1.80 (rendered 3.36); AAPL 8-K quarterly revenue $109.4B (rendered $364.4B — the 9M variant).

### The fix is two-part, and PWR demonstrates both in one name

PWR's **operating cash flow has no 90-day bucket for 2026** — only H1 ($1,487,188,000) — because 10-Q cash-flow statements are cumulative by construction. Its rendered `+176.0%` is H1-vs-H1, same-duration, and arithmetically correct. So "always prefer Q" would break it.

> **Rule.** For `[flow]` concepts, prefer the bucket whose duration matches the filing's fiscal quarter (~90d) **and** whose end date equals the anchor date. Where only a cumulative bucket exists, render it and fire the `[6M YTD]` / `[9M YTD]` label that §11 already pre-registers. YoY stays same-duration either way — that half already works. The section header must state the period the block actually reports.

### Scope, and why it grows

`[V]` — affected iff the latest periodic is **Q2 or later in the filer's fiscal year**. Q1 filers are immune because YTD ≡ Q1; annual filers are immune.

| | Names |
|---|---|
| **Affected (6)** | AAPL (9M as Q3), FTI, GM, PM, PWR, RTX (H1 as Q2) |
| **Immune (9)** | CORN, DOW, GLD, JPM, NVDA, SND, WMT (Q1) · MSFT, NKE (10-K FY) |

**The footprint expands without any code changing.** WMT, JPM, NVDA, SND, CORN and GLD all file their next periodic inside the E4-2 measurement window and roll from immune to affected. Unfixed, 6/15 becomes roughly 13/15 by the first read. This is the load-bearing argument for DP-3C-k and it was not visible before this session.

### It reached the model

- FTI: *"long-term debt down 33%, operating income up 34%"* — both H1 statements figures (−32.6%, +33.7%), read as current-quarter.
- AAPL: *"16% revenue growth, 50.1% gross margin, and 43% operating cash flow growth"* — the first two are the 8-K's quarterly figures, the third is the statements block's 9M `+43.1%`. Three figures in one clause, two periods, no marker.
- GM: risk flags *"operating income −20% YoY, operating cash flow −28.3% YoY"* — H1.

## 3 · F-1 · Budget exhaustion drops the statements block

`[V]` The warning fired 09:49:12.540 during JPM. Split at that boundary:

| Group | Names | `fin=` in E tag |
|---|---|---|
| Pre-budget | AAPL, CORN, DOW, FTI, GM, JPM | all present |
| Post-budget | MSFT, NKE, PM, PWR, RTX, SND, WMT, NVDA | **all absent** |
| Post-budget, no recompute needed | GLD | present — the control |

Mechanism, confirmed by standalone reproduction: the eight dropped names **all re-logged `schema N != 6 — recomputing` when run individually**, while the six pre-budget names did not. The in-run recompute started, was abandoned at budget, and **never wrote to cache**. GLD is the control that isolates it — post-budget, nothing to recompute, section intact.

`[V]` **Cache writes do persist.** A second `--ticker MSFT` logged no recompute line. All 15 covered names are now warm at `EXTRACT_SCHEMA` 6.

### The budget is measuring the wrong thing

Prefetch ended 09:47:08.210; warning at 09:49:12.540 = **124.3 s wall clock**, containing 8 Claude signal calls (~94 s), 8 news fetches (AAPL alone 10.2 s), and the quote/price-history round trips. EDGAR fetch/extract is roughly **7 s of it — about 6% of a budget nominally allocated to EDGAR.** Raising `EDGAR_MAX_SECONDS` buys more Claude API time. Hence DP-3C-j.

This is also a cold-cache-at-quarter-boundary problem that §18 already anticipates in general terms. Warming the cache clears today; it does not clear the next schema bump or the next new quarter. The structural fix is per-ticker visibility: `fin=degraded` must be distinguishable from `fin=none`, because a tag that omits `fin=` for two different reasons is a tool reporting a value it did not compute.

**Proposed tag format for step 4:**

```
E[8k=1@2026-07-23; form4=+0/-5@2026-07-28; periodic=10-Q@2026-07-23; fin=9@2026-06-30]
E[8k=0; form4=1f@2026-07-14; periodic=10-Q@2026-05-20; fin=degraded]
E[no filings]
```

**One disambiguation the amendment forces.** E4-2 defines ADJACENT as an 8-K **or Form 4** filed within K = 5 trading days, with no restriction to open-market transactions. So `form4=…@D` must carry the date of the most recent Form 4 of **any** transaction code — including grants (A), option exercises (M) and tax withholding (F), which never move `net direction`. Otherwise the tag's date and the endpoint's definition disagree, and the disagreement will not surface until the E4-2 read.
